# Claude Desktop preview

Desktop is an optional preview. For a **local Gateway-mode `helper-script` pilot**, an [existing Windows Desktop configuration](windows-desktop-pilot.md) successfully used a native Entra helper and Chat without registry policy or a new OIDC client. That path still needs an authorized gateway token, installed helper and Azure CLI session; it did not test Code-tab tools, Cowork, refresh or revocation. The alternative managed **browser-OIDC** profile below requires a Desktop enterprise app, public-client registration with redirect URI `http://127.0.0.1/callback`, delegated consent, pilot devices, and endpoint management. This repository does not install Desktop, create its Entra registration, or apply registry/profile changes; generated OIDC files were not applied in the local pilot.

**Support versus verification:** Windows registry and macOS `.mobileconfig` generators are available. The [26 October dynamic discovery check](windows-desktop-pilot.md#2026-10-26-dynamic-discovery--api-and-picker-verified) verified a four-model picker with **Opus 5.5 selected** on Windows Desktop **3.6556.2.0**, using the actual **local Gateway/helper-script profile**, not generated MDM/OIDC. It sent no inference. Actual macOS device/native-auth/picker behavior is untested. This repository provides/validates no Linux Desktop installer or configuration; use the [Terminal integration](claude-code-managed-settings.md) there. See the [coverage table](../README.md#repository-integration-coverage-versus-live-discovery-verification).

```bash
python3 scripts/desktop/generate_managed_config.py \
  --gateway-url https://gateway.example/claude \
  --tenant-id 11111111-1111-1111-1111-111111111111 \
  --desktop-client-id 22222222-2222-2222-2222-222222222222 \
  --delegated-scope api://33333333-3333-3333-3333-333333333333/Claude.Access \
  --deployment-org-id 44444444-4444-4444-4444-444444444444 \
  --organization "Example Corp" \
  --sonnet-model sonnet-deployment --opus-model opus-deployment --haiku-model haiku-deployment \
  --output-dir out/desktop
```

For owner-approved **automatic discovery**, first back up and review existing client policy, then append `--enable-model-discovery` to this generation command. The three `--*-model` arguments may be omitted in discovery mode; they remain required for the default static mode. Discovery keeps the existing string `modelDiscoveryEnabled="true"` contract and omits `inferenceModels`; Windows output also removes the old value in the selected registry scope. An explicit `inferenceModels` list wins over discovery, including one delivered by higher-precedence policy. Neither file is applied by generation. The actual local pilot's app-normalized boolean `true` is a separate configuration path, not a reason to change this generator or import OIDC policy into that profile. Fully quit Desktop, including background processes, then restart to refresh after approved deployment/configuration; closing a window may leave the app running. Gateway freshness includes a 30-second cache plus ARM propagation and client startup, not open-picker polling. See [discovery and rollout limits](model-discovery.md#client-opt-in-only-after-the-endpoint-is-published).

For the **OIDC branch only**, enable `CLAUDE_DESKTOP_DELEGATED_AUTH_ENABLED=true` with `CLAUDE_DESKTOP_CLIENT_ID` and the short delegated-scope claim value in `CLAUDE_DESKTOP_DELEGATED_SCOPE`. Assign pilot users, grant consent for the exact full scope, and validate the generated profile/registry policy against the pinned Desktop version. Deploy generated files with MDM/GPO, verify its managed configuration report, then test inference, refresh, and revoked access before any expansion. Do not apply the broader repository role-OR-Desktop policy blindly to the strict live CLI-only pilot.

For a **single Windows user-profile pilot**, append `--windows-scope user --disable-cowork` to the command above. This generates a UTF-16LE `.reg` targeting `HKEY_CURRENT_USER\SOFTWARE\Policies\Claude` and sets `coworkTabEnabled=false` in both Windows and macOS outputs (leave `--disable-cowork` off to retain the existing default). The default `--windows-scope machine` instead targets `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Claude`; **any machine policy overrides the full user policy**, not only matching values. Confirm no machine policy before testing the user scope. Run the import only as the **pilot user's** Windows account (not an elevated different account); organizational policy may restrict writing HKCU policy values or require approved elevation, so stop and coordinate with endpoint management rather than importing into another account or hive. Restart Desktop, and check its managed-configuration report and actual login/inference. Windows 11 MSIX Desktop 2.7032 is a pilot host, not proof that the embedded Claude Code runtime meets the separate `>=2.1.280` model requirement; verify that runtime independently. A generated policy alone does not prove working auth or inference.

For rollback on a fresh pilot host, sign out of Desktop first, then import `claude-desktop-managed-remove.reg` under the **same scope and user**; it removes only generated value names and leaves other values in the policy key intact. Removing policy **does not delete cached tokens**; follow your organization's session/token revocation process separately. Import overwrites any existing values with the same names, and the removal file **does not restore overwritten values**. Back up existing policy values before importing; on a previously managed host use that backup to restore them instead of treating the removal file as a complete rollback. Neither file is imported by this generator.

The role-free Desktop branch checks client ID plus scope, **not user assignment**. Its access gate relies on external Entra assignment and consent controls. Identify separately the Desktop public-client registration/service principal (`CLAUDE_DESKTOP_CLIENT_ID`) and the gateway resource API registration/service principal (the audience app exposing the delegated scope). Entra owners must document and configure the applicable assignment-required settings, assigned users/groups, and delegated consent for this exact client/resource pair; this repository does not provision or verify those controls.

Require actual token-acquisition and inference tests for assigned and unassigned users without the gateway app role before rollout. Otherwise the role OR branch masks a Desktop assignment defect. Test both supported actor versions where used. Existing issued access tokens may remain valid after assignment or consent removal; test expiry, refresh and revoked access explicitly rather than promising immediate revocation.

## macOS managed preview rollout

The macOS path is the generated **browser-OIDC** `.mobileconfig`, not the Windows registry or the Windows local helper-script pilot. Use Python **3.10+** to generate it, and an organization-approved Desktop build for the device's architecture. Claude Code's terminal settings do not configure Desktop; a working terminal session is not evidence that Desktop authentication works. Do not copy Windows local profile metadata into a Mac or rely on shell exports for a Finder-launched app.

1. Confirm the OIDC prerequisites and APIM authorization branch above with the Entra/gateway owners. Record macOS version, architecture, Desktop version and deployment organization UUID. Keep the UUID stable across updates: it determines the profile and payload identifiers, allowing a discovery update to replace the same managed profile.
2. Generate the configuration above with `--disable-cowork` for a Chat-only pilot. Add `--enable-model-discovery` and omit the three model arguments if the owning gateway's authenticated `/v1/models` endpoint has been published and verified. Generation also emits Windows files; deploy **only** `claude-desktop-managed.mobileconfig` to macOS.
3. Check the file on a Mac before deployment: `plutil -lint "/absolute/path/to/out/desktop/claude-desktop-managed.mobileconfig"`. The generator emits an unsigned profile, not an installed or trusted policy. Review/sign/distribute through the approved MDM process (for example, Intune or Jamf). For a permitted manual pilot, use the organization's supported System Settings profile-installation flow; do not bypass enrollment or profile restrictions.
4. Back up the prior profile and record its identifier. Fully quit Desktop with **Quit Claude / Command-Q**, deploy the replacement, then launch it as the pilot user. Check the installed profile and Desktop's effective managed-configuration report for `com.anthropic.claudefordesktop`. For discovery, verify `modelDiscoveryEnabled` is enabled and no effective `inferenceModels` list remains in another policy. Merely generating or linting the plist does not prove native policy recognition.
5. Complete browser sign-in, verify the actual picker contains the gateway deployment IDs, select a model, and send an approved Chat request. Record status/version/model metadata only, never tokens, cookies or raw auth logs. Test streaming, cancellation, restart, sleep/wake and token refresh before expanding the pilot; Code-tab tools and Cowork need separate acceptance tests.
6. Rehearse rollback by restoring the previous MDM profile with the **same deployment organization UUID**, fully quitting and restarting Desktop, and checking auth and inference again. To return from discovery to a fixed list, regenerate without `--enable-model-discovery` and supply all three model names. Do not remove all management as a shortcut. Profile replacement/removal does not revoke cached tokens; follow the separate Entra session/revocation process.

### Discovery and product acceptance gates

On a controlled test gateway, verify add/remove of an approved successful Claude deployment in the bound Foundry account appears after ARM propagation, the 30-second gateway cache, and a full client restart. Do not delete production pins for this test. Also test an unavailable inventory endpoint, an empty inventory, and revoked access; stale or built-in picker entries must not be counted as successful discovery. Pins are not automatically upgraded, and discovery does not deploy models. For Terminal, separately measure cold and warm startup against its default three-second discovery deadline; macOS Desktop success does not establish terminal compatibility.

The repository's macOS/Linux CI job exercises fake-CLI helper behavior and generated settings/profile round trips without Azure access or installed Claude clients. It does **not** certify macOS Desktop, real Entra refresh, or live discovery. Promotion requires device evidence and the [production-readiness gates](production-readiness.md); macOS Desktop remains optional preview until that evidence exists.
